# v9.4 Modal handoff: calibrate, label, re-stage

Operator runbook for the only v9.4 step that needs a GPU. Plan:
`docs/plans/v9.4-dedup-label-completion.md` (D4a model choice, D5 verification,
D7 calibration gate). Everything here is **staging**: nothing publishes to the Hub.

Run it on your own machine. The Modal client speaks gRPC, and the cloud agent's
egress proxy does not, so the agent cannot run these steps.

## What this run produces

| step | work | GPU | projected cost |
|---|---|---|---:|
| 0 | pre-download Qwen3-32B-FP8 weights into the Modal cache volume | none (CPU) | cents |
| 1 | **calibration**: label 40 golden CUAD contracts | 1×H100 | ~$0.98 |
| 2 | score calibration locally. **STOP unless CUAD status is `pass`** | none | $0 |
| 3 | label the 89 pending SEC EDGAR EX-10 contracts (40 + 40 + 9) | 1×H100 | ~$2.64 |
| 4 | 25 flagged intents + 96 intent calibration rows, two passes each (242 short calls) | 1×H100 | < $1 |
| 5 | re-stage with every journal, run gates, stop the app | none | $0 |
| | **total** | | **~$4.60** |

These are projections from the sandbox cost model (`GPU_USD_PER_HOUR = 3.95`, a
420 s cold boot and a 120 s scaledown per step), not measurements. The budget is
your $30 monthly Modal credit. **Hard stop:** if the Modal usage page shows more
than **$2.50** after step 1, stop and send back what you have. The cost model
would then be off by more than 2×, and steps 3–4 would need re-planning.

Built-in guards, all on by default:

- each `gt_label_ex10.py` invocation sends one chunk: at most 40 documents, a
  $2.00 projected-spend cap (`--usd-cap`) and a 45-minute wall cap;
- the Modal app scales to zero (`min_containers=0`, one container max, 120 s
  scaledown), so an idle app costs nothing;
- the deploy refuses a drifted posture (`assert_posture`): one H100,
  `Qwen/Qwen3-32B-FP8`, 8 sequences, 32k context, fp8 KV, thinking off.

Why an H100 and not something cheaper: the 32B FP8 checkpoint fits one H100 with
the 32k window and runs native FP8. An L40S would need a 4-bit AWQ build (slower,
lower fidelity), and an A100 emulates FP8. The H100 is the cheapest **per
document** of the three, not just the fastest. The retired 14B model failed
re-verification on 126 spans, so a smaller model is not an option (plan D4a).

   `Mailroom-Corpus-EDA`.

   ```bash
   cd local-mailroom-sandbox && python3 -m venv .venv && .venv/bin/pip install -e ".[dev]" modal
   ```

3. Build the v9.3 base and the v9.4 stage. This reads the public dataset, needs no
   token and costs nothing:

   ```bash

   ```

   ```bash
   cd Mailroom-Corpus-EDA && .venv/bin/python scripts/build/build_v9_4_dedup_labels.py
   ```

   ```bash
   cd Mailroom-Corpus-EDA && grep -o '"stage_digest": "[0-9a-f]*"' data/v9_4/v9_4_report.json
   ```

   `0fcfdb558d59302b6ea8454a697a1c8473691d72c25d76ac697e56f64f08d4bd`, the one in
   the committed `docs/reports/audits/v9_4_dedup_label_audit.json`. If it differs,
   your stage is not the one the queues were cut from. Stop and report it.

4. Authenticate Modal. **Rotate the token that was pasted into chat earlier**

## Step 0: preflight and weights (no GPU)

All commands from here run in `local-mailroom-sandbox` unless noted.

```bash
.venv/bin/python deploy/modal_gt_labeler.py --check
```

Expected: `ok sandbox-vllm-gt-labeler Qwen/Qwen3-32B-FP8 x1 H100`. Anything else
means you are on the wrong branch. Stop.

```bash
.venv/bin/python -m pytest -q tests/test_gt_labeler.py
```

```bash
modal run deploy/modal_gt_labeler.py::download_model
```

This is a CPU-only download of about 33 GB into the `hf_cache` volume, so the first
GPU boot does not pay for it.

## Step 1: deploy and calibrate (GPU, ~$0.98)

```bash
modal deploy deploy/modal_gt_labeler.py
```

Copy the `serve` URL that the deploy prints, and add `/v1`:

```bash
export VLLM_BASE_URL="https://<workspace>--sandbox-vllm-gt-labeler-serve.modal.run/v1"
```

Confirm what the endpoint actually serves before sending any work. The first call
cold-boots the H100, which takes up to about 7 minutes. Retry until it answers:

```bash
curl -sS -H "Authorization: Bearer $VLLM_API_KEY" "$VLLM_BASE_URL/models"
```

The response must list `Qwen/Qwen3-32B-FP8`. Journal records are stamped with the
posture model, so this check is what proves the stamp is true.

```bash
Q=../Mailroom-Corpus-EDA/docs/reports/audits/v9_4_queues
P=../Mailroom-Corpus-EDA/data/v9_4/stage/parquet
```

```bash
.venv/bin/python scripts/gt_label_ex10.py --queue $Q/cuad_calibration.jsonl --parquet $P --out reports/gt-labeler/v9_4-cuad-calibration-qwen3-32b.jsonl
```

The last line reads `journal has N/40 accepted`. Rejected documents still count:
they score as misses. Every one of the 40 needs a record (accepted or rejected),
or calibration is `incomplete`. If the run stopped early (wall or $ cap), run the
same command once more; it resumes from the journal.

**Check the Modal usage page now** (hard stop above $2.50).

The calibration journal is never ingested as labels. Its 40 rows are expert gold,
and gate (b) fails the stage if a golden CUAD row changes.

## Step 2: score calibration (local, $0). The go/no-go gate

```bash
cd ../Mailroom-Corpus-EDA && .venv/bin/python scripts/build/build_v9_4_dedup_labels.py --cuad-calibration-journal ../local-mailroom-sandbox/reports/gt-labeler/v9_4-cuad-calibration-qwen3-32b.jsonl
```

```bash
cd ../Mailroom-Corpus-EDA && grep -A4 "^## Calibration" docs/reports/audits/v9_4_dedup_label_audit.md
```

Go only if the CUAD line shows `'status': 'pass'`: micro-F1 ≥ 0.75 **and**
micro-precision ≥ 0.80 on all 40 documents, from `Qwen/Qwen3-32B-FP8`.

- `fail`: **stop.** Run `modal app stop sandbox-vllm-gt-labeler` and send back
  the journal (see "Send back"). Do not lower the floors, retry for a better
  number, or swap models ad hoc. The next tier is a 70B on 2×A100-80GB, which needs
  a new, reviewed sandbox posture (plan D4a).
- `incomplete`: some of the 40 have no record. Re-run step 1's command.
- `model_mismatch`: the journal came from another model. Check step 1's `/models`
  output.

## Step 3: EX-10 labels (GPU, ~$2.64), only after a pass

Back in `local-mailroom-sandbox`, with the same shell (`Q`, `P`, `VLLM_*` set):

```bash
.venv/bin/python scripts/gt_label_ex10.py --queue $Q/ex10_remaining.jsonl --parquet $P --out reports/gt-labeler/v9_4-ex10-cuad-labels-qwen3-32b.jsonl
```

Run it once per chunk. Each run prints `chunk K docs=N projected_usd=…`, then
`journal has A/89 accepted`. Repeat until it prints `queue empty`, with **at most
4 runs**. A labeler reject is retried in the next run, so a fourth run may be needed
if early chunks had rejects. Whatever is still rejected after 4 runs stays
`pending_annotation`, and that is an acceptable outcome. The output file name must
stay exactly `v9_4-ex10-cuad-labels-qwen3-32b.jsonl`, which the EDA build
auto-discovers.

## Step 4: intents (GPU, < $1)

Still in the same shell (the app is warm if you go straight on):

```bash
cd ../Mailroom-Corpus-EDA && VLLM_BASE_URL="$VLLM_BASE_URL" VLLM_API_KEY="$VLLM_API_KEY" .venv/bin/python scripts/build/build_v9_4_dedup_labels.py --run-intent-pass --cuad-calibration-journal ../local-mailroom-sandbox/reports/gt-labeler/v9_4-cuad-calibration-qwen3-32b.jsonl
```

This labels the 25 `flagged_review` rows and the 96 manual calibration rows (two
passes each) into `data/v9_4/llm_raw/intents_{flagged,calibration}.jsonl`. It is
checkpointed: a re-run skips rows already written. Then it re-stages with every
journal. Intent labels are ingested only if intent κ ≥ 0.75 on the 96 manual rows.
Otherwise they are held and the 25 rows stay flagged.

Then stop the GPU:

```bash
modal app stop sandbox-vllm-gt-labeler
```

## Step 5: gates (local, $0)

```bash
cd ../Mailroom-Corpus-EDA && .venv/bin/python scripts/audit/verify_v9_4_conformance.py --require-publish-ready
```

```bash
cd ../Mailroom-Corpus-EDA && .venv/bin/python -O scripts/audit/verify_v9_4_conformance.py
```

(a)–(g) must be `PASS`. (h) is `PASS` only when every calibration that applies
passed. A failing gate raises with the reason, so send the output back verbatim.

```bash
cd ../Mailroom-Corpus-EDA && .venv/bin/python -m pytest tests/test_v9_4_revision.py -q -o addopts=""
```

The e2e test pins `pending_cuad == 89` for an unlabeled stage, and it builds its
own unlabeled stage, so it still passes after your run.


```bash
cd ../local-mailroom-sandbox && git add reports/gt-labeler/v9_4-*.jsonl && git commit -m "v9.4: Qwen3-32B-FP8 calibration, EX-10 and intent journals" && git push origin claude/focused-keller-7g1ce1
```

Also send:

- the step 2 calibration lines and the step 5 gate output;
- the Modal usage-page total for the run.

With the journals pushed, the EDA side re-stages offline from them
(`--intent-journal`, `--intent-calibration-journal`, `--cuad-calibration-journal`),
rebuilds the audits twice for determinism, and commits them. The spot-check pack
`docs/reports/audits/v9_4_label_review.{md,csv}` (a 20% sample of ingested EX-10
spans) then needs a human `reviewer_verdict` pass before any promotion.

## If something goes wrong

| symptom | action |
|---|---|
| `--check` prints a different model/GPU | wrong branch or a drifted shell env: `unset` the `MODAL_VLLM_*` vars, check out the branch, re-check |
| deploy fails on `huggingface-secret` | prerequisite 5 |
| `/models` keeps timing out after 10 min | `modal app logs sandbox-vllm-gt-labeler`; stop the app; send the log |
| HTTP 401 from the endpoint | `VLLM_API_KEY` ≠ the `MODAL_VLLM_API_TOKEN` exported at deploy time; re-export both, redeploy |
| `stopping before the next chunk: est $…` | the per-run cap worked; just run the command again |
| spend climbing with nothing running | `modal app stop sandbox-vllm-gt-labeler`; check `modal app list` shows it stopped |
| stage digest mismatch (prerequisite 3) | stop; do not label against a different stage |
