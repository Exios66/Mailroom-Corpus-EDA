## 0. Scope and the one law

This is the **label-presence-layer** revision of the gt_presence key-set law
(the single deepest defect in the eval-format findings: the v9.2-era uniform
3-key corporate assertion meant *published rows structurally could not label
entity fields*; see `reports/Mailroom dataset eval format.md`, "One schema
module…" + Conclusion). What changes:

- the EDA platform registry (which presence keys `corporate_record` rows may
  express), driven from the shared dojo schema registry;
- the EDA-side relabel equivalents that re-platform the verified v9.2.1
  content onto the producer;
- the manifest, which adopts `labels_version` alongside the dataset version;
- the card, which documents the presence vocabulary verbatim.

What does **not** change: the row set, identity, doc content, and every
populated label VALUE — the corpus stays exactly the published
`corporate-labels-v9.2.1` content (row set / identity / content unchanged, the
v9.2.1 line itself). The dataset `version` line stays the v9 family; no new
parquet configs (the manifest/README config rows are untouched).

## 1. Decisions recorded

- **D-registry.** `FIELD_KEYS_BY_CLASS["corporate_record"]` grows from the
  3-key semantic trio to the dojo union: trio + 6 entity-core keys
  (`entity_name`, `record_type`, `effective_date`, `signatories`,
  `jurisdiction`, `filing_number`) + the 31 distinct per-subclass extension
  entities enumerated from
  `llm_dojo_scoring.corporate_record_schema.SUBCLASS_SCHEMAS` — 37 keys,
  `ALL_GT_FIELDS` 20 → **57**. Registry lives in
  `src/mailroom_eda/corporate_presence.py`, **sha-pinned** to the dojo module
  (`92dbfa9c…` at dojo rev `8e6566c1…`); a facet-comparison parity check
  (in-process or via the dojo's own venv) proves mirror == live module when
  the sibling checkout is present (`scripts/audit/verify_v9_3_conformance.py`
  gate `(+)`; the hub#57 skip-safe test convention). Places that hardcode the
  corporate 3-key set for the *presence* layer (gt_presence FIELD_KEYS /
  verify_presence_codes / v9.2 sidecar registry expectations) are driven from
  the registry; v9_build's build-time `CLASS_GT_KEYS` trio is a *different*
  concept (semantic-trio completeness gate for new draws, not the presence
  map) and stays as-is — recorded here as an out-of-scope decision.
- **D-superset-presence (the relaxed law).** `verify_presence_codes` (v9.1
  module) no longer asserts `set(presence) == set(ALL_GT_FIELDS)`. The v9.3
  law: every row carries **ALL `BASE_GT_FIELDS` keys** (the 20-key uniform
  v9.1/v9.2 base — the base law required, never silently dropped); keys ⊆
  `ALL_GT_FIELDS` (unknown keys rejected); **only corporate rows may carry
  the entity keys**; every code ∈ the published vocabulary; `genuine_gap`
  and the internal `unlabeled` sentinel must never ship. Non-corporate
  regenerations stay byte-stable (uniform base maps only).
- **D-unstated-blank.** The dojo scorer-side fifth regime — *unstated-blank ⇒
  unlabeled* — is now expressible by the producer: blank entity fields with
  no absence statement are **omitted** from the map (`row_gt_presence` drops
  the `unlabeled` sentinel cells; `classify_field` returns them for
  corporate-entity cells, `not_applicable` only for inapplicable CORE keys
  per the subclass map — extension keys of foreign subclasses are unlabeled,
  never `not_applicable`). This mirrors `corporate_record_relabel` exactly.
- **D-passthrough-of-verified-bytes.** The staging payload transfers the
  verified branch label content byte-for-byte (`ground_truth_hardened.jsonl`,
  bundles/streams/fixtures + parquet read-only), while the *builder still
  re-derives every corporate row independently* via the EDA relabel
  equivalents from the v9.2 base and proves **raw-line byte equality** — so
  gate (d) is a real rebuild proof, not a copy. Parquet is not re-written
  (the EDA writer's bytes ≠ the branch writer's bytes at the container
  level; rows are identical — restaging would change shas without changing
  labels; recorded as the honest passthrough choice, like v9.1/v9.2
  read-only bundles).
- **D-labels_version (FAIR).** The manifest gains
  `labels_version: v9.3 corporate gt_presence presence-layer …` next to the
  unchanged `version` line (v1, canonically v9 of the corpus family) —
  separating label waves from dataset revisions (Data Science Journal 2026
  practice; the anti-pattern is one conflated number). The `revision:` line
  names the presence-layer change. `built_utc` refreshes.
- **D-precedence-honesty.** The entity presence on the 450 rows uses ONLY the
  v9.2.1 relabel's derivations (the `entity_name`/`record_type` pins + the
  not-applicable core marks). No new label facts are invented anywhere in
  the pipeline; `relabel_all_rows` is guarded by a shape check that HARD
  STOPS on any corporate-row change outside `gt_fields` /
  `expected_subclass` (the 12 verified conflict re-assignments), on any
  non-corporate modification, or on any pre-existing corporate gt value
  outside the relabel-owned keys.

### 6.1 `row_gt_presence` top-level-read caveat (Sonnet finding 5)

`gt_presence.presence_law_problems`, `classify_field`, and
`gt_presence.row_gt_presence` read label values from the TOP-LEVEL keys of
the row they are handed (`row.get(field)`), so a consumer must flatten
`gt_fields` onto the row before any re-derivation. The v9.1-builder path
does exactly that: `v9_1_revision.revise_row` builds a flattened
`presence_probe = dict(gt)` (label values top-level, post-B1/B4) and
serializes `json.dumps(row_gt_presence(presence_probe))` INTO `gt_fields`;
the strict-audit path (`gt_quality.load_snapshot`) likewise explodes the
parquet `gt_fields` JSON string into flat columns before `audit_row` runs.
Conversely, handing either helper a row in the SHIPPED hardened-JSONL shape
(labels nested under `row["gt_fields"]`) yields empty reads for every label
— every populated cell would classify as blank or gap — so the derived
codes are meaningless. Downstream re-derivations (scorers, audits, backfill
tools) must therefore either flatten first or consume the shipped
`gt_presence` code map directly; the law helpers themselves never unwrap
`gt_fields`.

### 6.2 coverage_matrix has no unlabeled bucket

`scripts/audit/coverage_matrix.py` has no `unlabeled` bucket by design:
corporate unlabeled cells (the unstated-blank regime) are aggregate-
parity-only for this revision — the EDA coverage matrix stays on the four
published codes, and the dojo-side audit that understands the fifth,
scorer-only regime is the backstop that proves unlabeled cells stay
excluded from scoring.

### 6.3 Historical rebuilds (runbook note)

The historical `v9.1` / `v9.2` tag payloads are NOT reproducible through
this branch's staging path: `build_all` here pins the v9.2 base sidecar and
the `corporate-labels-v9.2.1` branch bytes and runs the v9.3
presence-regime laws, so regenerating a v9.1 or v9.2 publication requires
checking out the respective tag and running that tag's own builder/runbook
(uniform-map law), never the v9.3 staging build. The relaxed superset law
is backward-compatible with those payloads (v9.3 reparses their uniform
20-key maps as lawful minimal maps); reproducing them wholesale is
tag-specific work.
