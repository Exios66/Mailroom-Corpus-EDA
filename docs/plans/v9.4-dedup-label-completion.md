# v9.4 — Dedup + label-completion revision (STAGING, 2026-11-04)

Module: `src/mailroom_eda/v9_4_revision.py`. CLIs:
`scripts/build/build_v9_4_dedup_labels.py`, `scripts/audit/verify_v9_4_conformance.py`.
Tests: `tests/test_v9_4_revision.py`. Input: the v9.3 stage (`data/v9_3/stage`).
Output: `data/v9_4/stage`. **Nothing publishes**: `--publish` raises.

## 0. Why

An external EDA of published v9.2 (`670e8bc6`), a CS graduate project notebook,
found four defects that every earlier revision had carried forward:

| finding | count on v9.3 stage | v9.4 action |
|---|---:|---|
| exact duplicate texts (same `content_sha256`, different filename) | 6 groups / 9 extra rows; one group spans train + test | removed |
| `"nan"` strings standing in for absence in `gt_fields` | 2,100 cells on 350 insurance rows (200 GNOTHEIA + 150 BDR) | set to `""` |
| SEC EDGAR EX-10 `cuad_clause_labels` = `pending_annotation` (issue #30) | 91 (89 after dedup) | filled from a verified Modal LLM journal where it passes |
| correspondence `intent_status = flagged_review` | 25 | two-pass Modal relabel (runbook below) |

Also fixed: `parquet/ground_truth/dataset_info.json` still declared the
`_published` feature that v9.2 C2 removed from the parquet.

## 1. Decisions

- **D1, the row set changes** (3,302 → 3,293; train 2,971 / test 322). This is the
  first revision since v9 that removes rows. It is a dataset-content change and
  needs a new revision tag at promotion.
- **D2, survivor rule.** In order:
  1. richest annotation (CUAD spans + MAUD answer count + populated presence cells);
  2. no copy marker such as `(1)`;
  3. `train` split;
  4. smallest filename.

  Survivors keep their v9.3 bytes, `document_id` and split. `dedup_removed.jsonl`
  ships in the payload with every removed copy, its survivor and any label conflict.
- **D3, conflicting expert annotations are not merged.** Two groups have identical
  text but different expert labels:
  - CUAD `ADUROBIOTECH…CONSULTING AGREEMENT(1).PDF` has 16 spans; the non-`(1)` copy
    has 14. The richer `(1)` copy survives.
  - MAUD `contract_148` / `contract_149` disagree on 15 of 17 shared questions and on
    `expected_subclass` (`mixed_cash_stock` vs `other`). `contract_149` survives
    (187 answers vs 156). **Someone who knows MAUD should confirm this choice**;
    the conflict is recorded, not resolved.
- **D4, `"N/A"` stays.** The 3 CMS outpatient `"N/A"` dates are a verbatim source
  marker (`v9_build`), not a placeholder.
- **D5, LLM labels are never trusted, only verified.** Serving lives in
  `local-mailroom-sandbox` (SAND-045, `sandbox-vllm-gt-labeler`,
  `Qwen/Qwen3-14B-AWQ`). This repo only re-verifies journals. A label is ingested
  only when:
  0. the journal record names the same `document_id` as the row it is filed
     under; the journal's sha256 and model are recorded in the audit;
  1. every span equals `doc_text[start:start+len(text)]` in *this* payload;
  2. every category is one of the 41 CUAD names read from the golden rows;
  3. spans are 4,000 chars or shorter, and `Document Name` sits in the opening 5,000 chars;
  4. light semantic probes pass (Governing Law mentions law/governing/jurisdiction;
     date categories carry a date or event trigger). Failing spans are dropped,
     never repaired;
  5. the labeler's own floor holds after drops (4 or more present categories, plus
     Document Name or Parties).

  Otherwise the row stays `pending_annotation`. A survivor can take the accepted
  record of its removed byte-identical copy (same text, same offsets).
- **D6, intent acceptance.** A relabel is accepted only when both passes agree on an
  in-vocabulary label (pass A: subject + body; pass B: body only), **and** the label
  either confirms the original or both passes have confidence ≥ 0.8. Otherwise the
  row stays `flagged_review`.
- **D7, calibration gates publishing, not staging.** The same model must be scored
  against expert labels:
  - CUAD category-presence micro-F1 ≥ **0.6** on 40 stratified golden contracts
    (≤32k band, seed 42);
  - intent Cohen's κ ≥ **0.6** on the 96 manual correspondence intents (only needed
    if any intent relabel is accepted).

  Until both are measured, gate (h) is `PENDING` and `publish_ready = false`.

## 2. Current staged result (no calibration yet)

- 76 of the 89 pending EX-10 contracts now carry verified CUAD maps; 13 stay pending:
  - 12 were rejected by the labeler: 10 had fewer than 4 categories, 1 recovered
    neither Document Name nor Parties, and 1 got an HTTP 400;
  - 1 fell below the floor after verification.
- Semantic probes dropped 17 spans. Inspected by hand, they are mostly wrong-category
  spans, for example a notices clause labeled Governing Law, or a non-disparagement
  covenant labeled Warranty Duration. The model mixes up categories. Calibration
  measures how often that happens in categories the probes don't cover.
- Spot-check pack: `docs/reports/audits/v9_4_label_review.{md,csv}`, a 20% sample
  with a `reviewer_verdict` column.
- Audit: `docs/reports/audits/v9_4_dedup_label_audit.{md,json}`.

## 3. Modal runbook (run on a machine where the Modal client can connect)

The Modal client speaks gRPC. The cloud agent's egress proxy does not support gRPC,
so these steps cannot run there. The queues they need are committed under
`docs/reports/audits/v9_4_queues/`.

```bash
# in local-mailroom-sandbox
modal token set --token-id <id> --token-secret <secret> --profile=exios66 --activate
modal secret create huggingface-secret HF_TOKEN=<hf token>     # once per workspace
export MODAL_VLLM_API_TOKEN=<choose a bearer token>
python deploy/modal_gt_labeler.py --check
modal deploy deploy/modal_gt_labeler.py
export VLLM_BASE_URL=https://<workspace>--sandbox-vllm-gt-labeler-serve.modal.run/v1
export VLLM_API_KEY="$MODAL_VLLM_API_TOKEN"

# 1) calibration: the model on 40 golden CUAD contracts (writes a separate journal, never gold)
python scripts/gt_label_ex10.py --queue ../Mailroom-Corpus-EDA/docs/reports/audits/v9_4_queues/cuad_calibration.jsonl \
  --parquet ../Mailroom-Corpus-EDA/data/v9_4/stage/parquet --out reports/gt-labeler/v9_4-cuad-calibration.jsonl
# 2) retry the 13 remaining EX-10 rows
python scripts/gt_label_ex10.py --queue ../Mailroom-Corpus-EDA/docs/reports/audits/v9_4_queues/ex10_remaining.jsonl \
  --parquet ../Mailroom-Corpus-EDA/data/v9_4/stage/parquet --out reports/gt-labeler/ex10-cuad-labels.jsonl

# in Mailroom-Corpus-EDA: 25 flagged + 96 calibration intents, then re-stage with every journal
.venv/bin/python scripts/build/build_v9_4_dedup_labels.py --run-intent-pass \
  --cuad-calibration-journal ../local-mailroom-sandbox/reports/gt-labeler/v9_4-cuad-calibration.jsonl
.venv/bin/python scripts/audit/verify_v9_4_conformance.py --require-publish-ready

modal app stop sandbox-vllm-gt-labeler
```

Each `gt_label_ex10.py` invocation is one chunk: at most 40 documents and a $2
projected cap on one L4. The intent pass is short emails, about 242 calls.

## 4. Gates (`verify_v9_4_conformance.py`)

- (a) row set: 0 duplicate shas, count = v9.3 minus removed, md5 split rule holds.
- (b) survivors byte-identical to v9.3, except allowlisted fill fields.
- (c) 0 placeholder cells.
- (d) presence key-set law holds, no `genuine_gap`.
- (e) every populated EX-10 CUAD map re-verifies verbatim.
- (f) ground_truth parquet equals the JSONL; `dataset_info` features equal the parquet columns.
- (g) manifest sha table recomputes.
- (h) calibration. `PENDING` blocks publishing only.

## 5. Out of scope

- The 800 synthetic insurance rows stay. They are documented as synthetic by design.
- Rows that omit inapplicable `gt_fields` keys follow the intentional v9.3 superset
  law and are left as they are.
- Near-duplicates are reported only: the audit lists any normalized-text collisions
  that are not byte-equal. On v9.3 there are none.
